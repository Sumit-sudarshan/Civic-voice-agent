# What I Am Not Building (and Why)

This project is a demo focused on the AI pipeline and how it is evaluated, not a finished production system. This document explains what I deliberately left out, why I left each thing out for this build, and what I would add if this were going to be used for real.

**Who would actually use this.** Citizens submit complaints and suggestions through the chat. A local leader and their staff go through those complaints on the dashboard and act on them. I also built a hidden page for myself to check how well the AI is performing.

**Who might try to misuse it.** Someone could spam the system with fake reports to make one issue look bigger than it is, someone could submit abusive messages, or someone could try to view the leader dashboard or citizens' personal details without permission. The sections below are the places where a real deployment would need to defend against exactly this.

## Login and accounts
There is no real login system for either citizens or leaders right now. On the citizen side, logging in just stores a name in the browser, there is no password and no real account on the backend. The leader dashboard has no login at all, anyone with the link can open it. I skipped this because building a proper login system is a well known problem with standard solutions, and I wanted to spend my time on the AI pipeline instead, which is the actual focus of this project. If I were building this for real, I would add phone number based OTP login for citizens, since the phone number is already being collected anyway, and a proper login system for leaders and staff that only lets each leader see complaints from their own area.

## Rate limiting
There is nothing stopping one person from submitting as many complaints as they want. I left this out because the demo only handles a small number of test submissions at a time, so it was not a real problem here. In a real version, I would limit how many complaints someone can submit based on their phone number or email, not their device or IP address, since IP addresses are shared between people and are easy to change.

## Blocking abuse and fake reports
Right now, the only protection against bad content is the gatekeeper checking each individual message as it comes in. There is nothing to detect bots, nothing like a CAPTCHA, and nothing to catch a group of fake accounts all reporting the same made up issue to push it up the priority list, other than the existing duplicate detection, which is not really designed for that. I left this out because bot detection and coordinated-abuse detection are largely infrastructure and behavioral-analytics problems, not an AI pipeline concern, and at the demo's test volume there was never a real coordinated-abuse pattern to design against or test. A real deployment would need actual bot detection and a way to spot coordinated fake reporting.

## Protecting citizen data
Every submission collects the citizen's name, phone number, and address, and all of that is stored as plain readable text in the database. Even rejected submissions, like spam or abusive messages, are kept for the record instead of being deleted. I left the data unmasked on purpose so I could actually demonstrate that things like duplicate detection and location matching work correctly using real looking data. In a real deployment, this data would need to be encrypted, the phone number would be hidden on the dashboard unless someone genuinely needs to see it, and there would need to be a clear policy on how long data is kept and when it gets deleted, along with getting proper consent from citizens.

## Handling scale
The whole system currently runs on one instance of the local model, processes submissions using FastAPI's basic background task feature, and stores everything in a single SQLite database file. If a lot of complaints came in at the same time, things would start queuing up behind that one model, and SQLite is not great at handling many things writing to it at once. I left this as is because the demo only needs to handle a handful of submissions at a time, not real traffic. A real deployment would need a proper task queue system with multiple workers, the ability to run more than one copy of the model at once, and a database like Postgres that is built to handle many simultaneous writes.

## Cost at real scale
Running the model locally does not cost anything per request, just the cost of the hardware and electricity to keep it running. Running the hosted model through Groq costs money for every request, and since each complaint triggers about four separate model calls, that cost adds up quickly the more complaints come in. I did not calculate real numbers for this since my testing volume is small, but the setup already supports splitting the work, using the free local model for the simpler steps and only paying for the better hosted model on the steps where it actually makes a meaningful difference.

## Emergency response
If someone's message looks like a real personal emergency, the system tells them directly to call the actual emergency numbers (112 or 108). It does not connect to any real emergency service, does not notify anyone, and does not do anything beyond showing that message. This is intentional. This project is a complaint tracking tool, not an emergency response system, and actually connecting to emergency services is a completely different kind of project with much higher stakes if something goes wrong.

## Visibility into failures
Right now, if something breaks, the only way to find out is by checking the application logs or noticing a flag in the database that says a record needs review. There is no dashboard showing how often things are failing over time, and nothing that automatically alerts me if a step starts failing a lot. I did not build this because it was not needed to demonstrate the core pipeline. A real deployment would need proper monitoring so failures get noticed quickly instead of being found by accident later.

## Routing complaints and following up automatically
Right now, a leader has to manually change the status of each complaint after reviewing it. There is no automatic routing to the correct department, and nothing follows up if a complaint sits unresolved for too long. In a real version, I would want each complaint to automatically get routed to the right department based on its category, for example an electricity complaint going straight to the electricity department, and if a complaint is not resolved within a set number of days, say ten, it should automatically get escalated to someone higher up so it does not just get forgotten.

## Assigning the responsible official by area
Right now, all complaints land in one dashboard for one leader, there is no step where the system figures out which specific person, for example the ward officer or department contact for that particular area, is actually responsible for it and routes the complaint to them directly. I left this out because doing it properly needs a jurisdiction map, which area or ward belongs to which official, for each department, and that mapping doesn't exist yet; it's a data and administrative problem separate from the AI pipeline itself. In a real version, once that area-to-official mapping is set up, the pipeline could match a complaint's extracted location and category against it and route the complaint straight to the concerned person automatically, instead of leaving it to a leader to manually forward.

## Evaluation methods I chose not to use
**The model's own confidence score.** I could have asked the model to also report how confident it is in each answer, and used a low confidence score to flag things for review. I chose not to do this because a small model's self reported confidence usually does not reflect how likely it actually is to be correct, it is not a reliable number on its own. I already have a separate, more reliable system that flags a record for human review whenever a step genuinely fails, so this would not have added much. This could be worth revisiting later, but only after properly checking whether the model's confidence scores actually line up with real accuracy.

**BLEU, ROUGE, and similar text comparison scores.** These are commonly used to check generated text, but I decided not to use them here for two reasons. First, they need one single correct reference sentence to compare against, and there is no single correct way to write a complaint summary, so there is nothing to compare it to. Second, these scores mostly reward matching the exact same words, but what I actually care about here is whether the summary got the facts right and did not make anything up, not whether it used the same wording as some reference answer. I would like to come back to this later and think about a scoring method built specifically for this kind of problem instead of borrowing one meant for something like translation.

## Voice input
The project is called Civic Voice Agent, but right now a citizen has to type their complaint, there is no option to actually speak it. I left this out mainly because of time, and because adding it properly is a separate problem on top of everything else I was already testing. To support voice, I would need to add a speech to text step before the message even reaches the language detection step, and that step would need to work reliably across English, Hindi, and Marathi accents, background noise, and people who are not used to talking to an app, which is a harder problem than getting the text pipeline right, and it would need its own accuracy testing separate from everything covered in section 4. It is also not a small model I could easily test locally the same way, converting speech to text well usually needs a bigger model or a paid API depending on the language, which brings back the same cost and infrastructure questions covered in the cost and scale sections above. The good part is that it would not require changing anything in the existing pipeline. Voice input would just become a new first step that turns audio into text, and everything after that point, language detection, the gatekeeper, and the rest of the pipeline, stays exactly the same. In a real version, especially since this is meant for people who may not be comfortable typing, I would treat this as one of the first things to add.

## How well this works in other languages
The examples I used to teach the gatekeeper to catch abusive or emergency messages are mostly written in English. I did test and measure how well the system classifies complaints correctly in Hindi and Marathi, and that part works well, but I have not separately tested how well it catches abuse or emergencies specifically in those languages, so that part might not work as well as it does in English.
